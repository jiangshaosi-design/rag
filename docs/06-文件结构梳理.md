## 二、分层依赖规则

```
        ui / app.py / api
              │
              ▼
           agent  ──────┐
              │         │
              ▼         ▼
      knowledge_base   database
              │         │
              └────┬────┘
                   ▼
                 config
```

| 层 | 依赖 | 不依赖 |
|----|------|--------|
| `config/` | `.env` | 任何业务模块 |
| `database/` | `config/` | `knowledge_base/`、`agent/` |
| `knowledge_base/` | `config/`、`database/` | `agent/` |
| `agent/` | `config/`、`knowledge_base/`、`database/` | `ui/` |
| `ui/`、`api/`、`app.py` | 全部下层 | — |

> `database/repository.py` 中的 `search_similar_question()` 反向调用了 `knowledge_base/embedder.py` 的 `embed_text()`，是唯一的跨层反向依赖（懒加载函数内 import，不构成模块级循环）。

## 三、逐文件职责说明

### 3.1 配置层

#### `config/settings.py`
全局唯一配置出口。启动时用 `python-dotenv` 加载项目根目录的 `.env`，所有配置项以类属性形式暴露，最后实例化为单例 `settings`。

- `_abs()` 辅助函数：把 `.env` 中的相对路径（如 `data/uploads`）转换为相对**项目根目录**的绝对路径，避免受当前工作目录影响
- 涵盖 6 组配置：DeepSeek LLM、阿里云 Embedding/视觉、MySQL、FAISS、分块参数、应用参数
- 所有配置项都带默认值，缺失 `.env` 时不会崩溃，但密钥为空会导致调用失败

**被依赖情况**：全项目所有模块都从这里读配置，无硬编码。

---

### 3.2 数据层

#### `src/database/connection.py`
MySQL 连接池管理与自动建表。

| 函数 | 职责 |
|------|------|
| `_ensure_database()` | 不指定 database 连接，执行 `CREATE DATABASE IF NOT EXISTS` |
| `_ensure_tables()` | 按 `;` 切分 `_CREATE_TABLES_SQL` 逐条执行建表 |
| `_create_pool()` | 先建库，再创建 `pool_size=5` 的连接池 |
| `init_db()` | 幂等初始化入口，由 `src/app.py` 在启动时调用一次 |
| `get_connection()` | 从连接池借出连接，**调用方负责 `close()`** |

`_CREATE_TABLES_SQL` 内联了三张表的 DDL（documents / chunks / chat_history），与 `scripts/init_db.sql` 内容一致 —— 前者保证开箱即用，后者供手动初始化。

#### `src/database/models.py`
三个 `@dataclass`：`Document`、`Chunk`、`ChatRecord`。纯数据容器，无方法。用于在层间传递结构化数据，`repository.py` 从 `cursor(dictionary=True)` 的结果直接 `Model(**row)` 构造。

#### `src/database/repository.py`
对三张表的全部 CRUD，按表分三段。

**Documents**：`add_document` / `get_document` / `list_documents` / `update_document_status` / `delete_document`

**Chunks**：`add_chunks_batch`（`executemany` 批量插入）/ `get_chunks_by_document` / `get_chunks_by_faiss_ids` / `delete_chunks_by_document`

> `get_chunks_by_faiss_ids()` 用 `ORDER BY field(faiss_id, ...)` 保持传入 ID 的顺序，使 MySQL 回查结果的顺序与 FAISS 相似度排序一致 —— 这是"检索结果按相关度排列"能成立的关键。参数需要传两份（`faiss_ids * 2`）。

**Chat History**：`add_chat_record` / `get_chat_history`

**缓存检索**（本文件里最复杂的部分）：
- `search_similar_question(query, top_n=3)` — 两阶段检索：
  1. **SQL 粗筛**：把问题按空格切词（长度 ≥2），用 `LIKE %kw%` 的 OR 条件捞出近期历史提问，`LIMIT top_n*3`
  2. **Embedding 精排**：对每条候选计算与当前问题的余弦相似度，仅保留 `> 0.85` 的
- `get_answer_for_question(question)` — 精确匹配历史提问，再取同 `session_id` 中该提问之后的第一条 assistant 消息作为答案

> ⚠️ 粗筛依赖空格分词，对没有空格的中文长句，分词结果往往是整句一个词，`LIKE` 匹配退化。这是已知限制。

### 3.3 知识库层

#### `src/knowledge_base/loader.py`
文档解析，三种格式各一个 `BaseLoader` 子类。

**`PDFLoader`（Docker MinerU）— 全项目最重的模块**

1. `shutil.which("docker")` 检查 Docker 可用性
2. `tempfile.TemporaryDirectory()` 建临时输出目录，挂载为容器 `/output`，PDF 所在目录挂载为 `/input`
3. `docker run --gpus all --rm ... mineru:latest mineru -p ... -o ... -b <backend>`
4. **逐行读取容器 stdout**，用正则 `(\S.*?):\s*(\d+)%.*?(\d+)/(\d+)` 解析 MinerU 进度条，把容器内进度映射到 pipeline 的 5%→15% 区间，实现真实进度反馈
5. 失败时从最后 20 行里提取含 `ERROR` 的行作为错误信息（过滤掉 `%|`、`it/s` 等进度条噪声）
6. `shutil.copytree()` 把 MinerU 输出持久化到 `data/mineru_output/doc_{id}/`
7. 读取 `{stem}.md`，调用 `_protect_markdown_tables()` 包裹表格
8. 图片处理：复制到 `data/images/doc{id}_{原名}` → 检查上限 → `ThreadPoolExecutor(max_workers=3)` 并发调用 Qwen-VL 描述（20s 超时）→ 把 Markdown 中的 `![](images/xxx.jpg)` 替换为 `[IMAGE: docX_xxx.jpg]: 描述`

> **设计要点**：先复制、再检查上限、最后才描述 —— 因为图片描述是**要花钱的 API 调用**，上限校验必须前置。注释中标了 ⚠️。

**`DOCXLoader`** — `python-docx` 读段落与表格，表格转 Markdown 并用 `[TABLE_START]/[TABLE_END]` 包裹（与 PDF 路径产出一致的中间格式）。该 loader 目前不提取图片（`image_paths` 恒为空列表）。

**`MarkdownLoader`** — 直接读取文本，无表格保护、无图片。

**辅助函数**：
- `_protect_markdown_tables(text)` — 逐行扫描，识别 `|...|` 格式的表格行与 `|---|` 分隔行，连续 ≥2 行则整体包裹保护标记
- `_describe_image(path)` — 惰性 import `image_describer`，异常吞掉返回 `None`（单张图失败不影响整篇文档）

**模块级注册表**：`LOADERS = {"pdf": PDFLoader(), "docx": DOCXLoader(), "md": MarkdownLoader()}`，`get_loader()` 按扩展名分发，`load_document()` 是统一入口。

#### `src/knowledge_base/splitter.py`
两层混合分块，核心目标是"保语义边界"与"补召回"兼顾。

1. `_protect_blocks()` — 用正则 `\[TABLE_START\].*?\[TABLE_END\]`（`DOTALL`）把所有表格块替换为 `__TABLE_BLOCK_N__` 占位符，避免被切断
2. `RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100)` 递归粗分，分隔符优先级：`\n\n` → `\n` → 中文标点 → 英文标点 → 空格
3. 对长度超 `SLIDING_WINDOW_SIZE(500)` 的粗分块，用步长 250 的滑动窗口再切（50% 重叠）
4. `_restore_blocks()` — 把占位符还原成原始表格

> **关键约束**：滑动窗口只在**单个递归块内部**滑动，不跨段落/章节边界 —— 这保证了窗口不会把两个不相关的章节拼在一起。

#### `src/knowledge_base/embedder.py`
阿里云 DashScope `TextEmbedding` 封装，`_BATCH_LIMIT = 10`（API 单次上限）。

- `_safe_call()` — 统一异常包装：网络异常、`status_code != 200`、响应结构异常三种情况都转成带中文说明的 `RuntimeError`
- `embed_text()` — 单条
- `embed_batch()` — 自动分批后 `np.vstack` 拼接
- `get_embedding_dim()` — 固定返回 1024（供向量库对齐维度）

#### `src/knowledge_base/image_describer.py`
`describe_image(path)` — 读图 → base64 编码 → 按扩展名推断 MIME → 组装 `MultiModalConversation` 消息（图片 + 中文描述指令）→ 返回描述文本。任何异常吞掉返回 `None`，保证批量描述时单张失败不中断。

#### `src/knowledge_base/vector_store.py`
FAISS 索引的创建、持久化与检索。

- `_create_index()` 用 `IndexIDMap(IndexFlatIP(1024))`：IDMap 允许自定义整数 ID 并支持删除，`IndexFlatIP` 配合 L2 归一化等价于余弦相似度
- **中文路径兼容**（本文件的特殊设计）：FAISS 的 C++ 层无法处理非 ASCII 路径。`_ensure_ascii_path()` 检测到中文路径时，把索引文件复制到 `%TEMP%/rag_faiss_cache/` 再做读写；`_sync_cache_to_source()` 在保存后同步回原路径。模块级 `_using_cache_dir` 标记当前是否走缓存路径
- `remove_from_index()` 依赖 `IndexIDMap` 的 `remove_ids()`，是删除文档时清理向量的基础
- `load_index()` 捕获读取异常并**删除损坏文件重建**，避免索引损坏后系统永久不可用
- `search()` 内部对查询向量再做一次 `normalize()`，返回 `[(id, score), ...]`，过滤掉 `-1`（FAISS 未命中标记）

#### `src/knowledge_base/pipeline.py`
入库与删除的流程编排，串联 loader → splitter → embedder → MySQL → FAISS。

`ingest_document(file_path, file_type, filename, on_progress)` 的 7 个步骤（`on_progress` 回调把百分比推给前端进度条）：

| 步 | 进度 | 动作 |
|----|------|------|
| 0 | 2% | 按 filename + status 去重检查 |
| 1 | 5% | 建 Document 记录（status=processing），`load_document()` 解析 |
| — | — | 图片数超 `MAX_IMAGES_PER_DOC` 则标记 error 返回 |
| 2 | 10% | `split_text()` 分块；超 `MAX_CHUNKS_PER_DOC` 则标记 error 返回 |
| 4 | 15–75% | 按 `_BATCH_LIMIT` 分批向量化，**每批回调一次进度** |
| 5 | 80% | 批量插入 chunks，再回写 `faiss_id = 该行的自增主键` |
| 6 | 90% | 载入或新建 FAISS 索引 → 归一化 → `add_with_ids` → 落盘 |
| 7 | 100% | `status=ready` |

> `faiss_id` 与 MySQL 主键的一致性：先插入拿到自增 ID，再 `UPDATE chunks SET faiss_id = str(id)`。**这意味着 FAISS 向量 ID 就是 `chunks.id`**，检索后可直接反查全文。

> 整段包在 `try/except` 中，异常时把文档标记为 `error` 并返回结构化错误，不让脏状态留在库里。

`remove_document(doc_id)` — 四路同步清理：MySQL（外键 `ON DELETE CASCADE` 会连带删除 chunks）→ FAISS `remove_ids()` → `glob` 匹配 `doc{id}_*.{png,jpg,jpeg,gif}` 删除图片 → `rmtree` 删除 MinerU 输出目录。

### 3.4 Agent 层

#### `src/agent/tools.py`
用 `@tool` 装饰器定义 4 个工具，函数 docstring 即为 LLM 看到的工具说明。

| 工具 | 签名 | 说明 |
|------|------|------|
| `search_knowledge_base` | `(query: str) -> str` | 向量化 → FAISS Top-K → MySQL 回查全文 → 格式化为 `[来源: 文件 \| 块N] (相关度: X.XX)` 分段文本，段间用 `\n\n---\n\n` 分隔 |
| `query_database` | `(sql: str) -> str` | **安全约束**：`sql.strip().upper()` 必须以 `SELECT` 开头，否则拒绝；结果超 20 行截断 |
| `manage_documents` | `(action: str) -> str` | `list` 列出文档；`delete:<id>` 删除（含存在性校验） |
| `check_history` | `(question: str) -> str` | 调用 `search_similar_question()`，命中则返回带相似度的缓存答案 |

> `search_knowledge_base` 返回的文本格式是与 `agent.py` 的**隐式契约** —— Agent 层靠正则解析这个格式来提取来源。修改格式必须同步改 `agent.py` 的解析正则。

#### `src/agent/agent.py`
Agent 组装与调用封装。

- `_SYSTEM_PROMPT` — 中文系统提示词，规定工具使用顺序（`check_history` 优先）、禁止反复检索、`[IMAGE:]` 标签处理、引用来源由前端展示不要在正文重复
- `_create_llm()` — `ChatOpenAI` 指向 DeepSeek 的 OpenAI 兼容端点，`temperature=0.3`
- `get_agent()` — 单例，`create_agent(model, tools, system_prompt)`
- `invoke_agent(message, chat_history)` — 主入口：
  1. 取最近 10 轮历史组装消息列表
  2. `agent.invoke(..., config={"recursion_limit": AGENT_MAX_ITERATIONS})`
  3. 捕获异常，把 recursion 超限翻译成中文提示
  4. **诊断日志**：打印消息总数、AI 消息数、工具调用次数、是否有文本答案（排障用）
  5. 遍历输出消息重建三类结构化数据：
     - `thinking` — `thought`（有 tool_calls 且带文本的 AI 消息）/ `action`（工具名 + 参数）/ `observation`（工具返回前 150 字）
     - `response_text` — **最后一条无 tool_calls 的 AI 消息**（即最终答案）
     - `sources` — 用正则 `\[来源:\s*(.+?)\s*\|\s*块(\d+)\]\s*\(相关度:\s*([\d.]+)\)` 从工具返回文本中提取
- `reset_agent()` — 置空单例

> `invoke_agent` 返回的 `{"response", "thinking", "sources"}` 是前后端之间的核心数据契约。

### 3.5 接口层

#### `src/api/server.py`
FastAPI 服务，为 HTML 版前端提供 REST 接口，同时挂载静态资源与 Jinja2 模板。

**页面路由**：`/`（落地页）、`/app`（问答页）、`/knowledge`（知识库管理页）

**API 路由**：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/chat` | 调用 `invoke_agent`，把来源中的 `[IMAGE:]` 标签追加到回答正文，并写入 chat_history |
| POST | `/api/documents/upload` | 校验扩展名 → 去重 → 落盘 → 起**后台线程**跑 `ingest_document`，立即返回 `task_id` |
| GET | `/api/documents/upload/{task_id}/status` | 轮询上传进度 |
| GET | `/api/documents` | 文档列表 |
| GET | `/api/documents/{id}/preview` | 优先读 MinerU 输出的 `.md`（前 3000 字），回退到数据库 chunks 拼接 |
| DELETE | `/api/documents/{id}` | 删除文档 |
| GET | `/api/stats` | 文档数 / 文本块数 / 向量数 |
| POST | `/api/chat/clear` | 重置 Agent |
| GET | `/api/chat/history` | 会话历史 |
| POST | `/api/evaluate` | 运行评估（auto / manual 两种模式） |

**并发设计**：上传是长任务（MinerU 解析大 PDF 可能 20 分钟），因此用 `threading.Thread(daemon=True)` 异步执行，进度写进模块级 `_upload_tasks` 字典，用 `threading.Lock` 保护读写，前端轮询 `/status` 拿进度。

### 3.6 评估层

#### `src/evaluation/metrics.py`

| 函数 | 指标 | 实现 |
|------|------|------|
| `precision_at_k(query, keywords, k)` | 精准度 | 检索 Top-K，统计命中期望关键词的块占比；返回带 ✅/❌ 标记的块预览 |
| `recall_crude(query, keywords, k)` | 召回率（近似） | 期望关键词中被检索结果覆盖的比例 |
| `faithfulness(answer, sources)` | 忠实度 | LLM-as-judge：把来源与回答一起喂给 DeepSeek，要求逐句核查后输出 `分数: X.XX` / `判定: ...`，正则解析 |
| `answer_relevance(question, answer)` | 答案相关性 | 问题与回答的 Embedding 余弦相似度，按经验阈值 0.8 归一化 |
| `evaluate_rag(cases, k, eval_faithfulness)` | 批量评估 | 逐用例跑四指标，汇总均值 |
| `print_eval_report(results)` | 报告 | 终端表格化输出 |
| `generate_test_cases(num_cases)` | 自动出题 | 从知识库随机抽中等长度文本块（100~2000 字），让 LLM 反向生成该块能回答的问题 |
| `evaluate_rag_auto(num_cases)` | 自动评估 | 自动出题 → 从源内容提取关键词作为 benchmark → 复用 `evaluate_rag` |

> 自动出题的价值：避免人工设计用例时"只测自己会答的题"的偏差。

#### `src/evaluation/run_eval.py`
CLI 入口（`python -m src.evaluation.run_eval`），内含 10 条针对 CH32V103 数据手册编写的手工测试用例 —— **这是示例数据，替换成你自己知识库的问题即可**。

### 3.7 前端层

#### `src/app.py`（Streamlit 版，推荐）
单文件应用，结构为：页面配置 → 约 200 行 CSS（深紫科技风）→ `init_db()` → 侧边栏 → 主对话区。

**侧边栏**：系统状态指标卡 + 连接指示灯、文档上传（带进度条与防重复处理）、已入库文档列表（带删除按钮）、清空对话、系统评估面板。

**主区**：状态条 → 空状态欢迎卡片（含 3 个示例问题按钮）→ 对话历史渲染 → 输入框。

**关键渲染逻辑**：用 `re.split(r'(\[IMAGE:\s*.+?\]:\s*[^\n]*)', text)` 捕获组分割回答文本，把 `[IMAGE: 文件名]: 描述` 标签替换为左右分栏的实际图片渲染；其余片段走 `st.markdown()`。

**防重复上传**：`st.session_state._processed_file` 记录已处理文件名，rerun 后跳过 —— Streamlit 每次交互都会重跑整个脚本，没有这个标记会重复入库。

#### `src/ui/`（HTML 版资源）
- `templates/` — 三个 Jinja2 页面模板
- `static/css/` — `style.css` 基础 + 三个页面各自的样式
- `static/js/` — `common.js` 工具函数 + 三个页面各自的交互逻辑（原生 fetch 调 REST 接口，无框架）
